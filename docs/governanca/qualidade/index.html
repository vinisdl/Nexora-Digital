Qualidade

Na Nexora, qualidade não é uma fase no fim do processo nem um departamento: é um conjunto de critérios verificáveis distribuídos pelo ciclo. Esta página junta todos eles num só lugar, para QA, Tech Lead e qualquer pessoa que precise saber "o que é bom o suficiente".

Por que distribuída?

No rollback do Nexora Sales, o Dev achava que o QA testaria, o QA achava que o Dev automatizaria, e o PO achava que tudo já estava testado quando chegou a ele. Critério que é de todo mundo acaba não sendo de ninguém. Aqui, cada critério tem um dono e um momento.

Os quatro gates​

GateMomentoDonoCritério resumidoVerificação
G1 · DoREntrada → EspecificaçãoPOProblema, valor, solicitante e critério de aceite registrados; categoria e prioridade definidasCampos obrigatórios no Azure DevOps + Checklist G1
G2 · Spec completaEspecificação → RevisãoDev (QA confere)Todo requisito com cenário; openspec validate --strict passando; tasks estimadasAutomática no pipeline + Checklist G2
G3 · Spec aprovadaRevisão → ConstruçãoTech LeadRevisores obrigatórios da categoria aprovaram o PR da specBranch policy + CODEOWNERS + Checklist G3
G4 · DoneEntrega → ConcluídoPO (aceite)Cenários passando + code review + aceite do PO + change arquivadaPipeline + Checklist G4

Crítica tem um critério extra antes do G3: o checklist de segurança (AF07).

Quem garante o quê​

PerguntaResposta no processo
Quem escreve os cenários?O Dev, na Especificação (com apoio de IA).
Quem garante que os cenários estão completos?O QA, na A3.2 · Revisar os cenários, antes do código.
Quem automatiza os testes?O QA é o dono dos testes dos cenários (AF08); o Dev apoia e escreve os testes unitários do próprio código.
Quem revisa o código?O Tech Lead ou um par, na A4.3 · Code review.
Quem diz que está pronto?O PO dá o aceite contra os cenários, e o pipeline confirma o resto do G4.

Estratégia de testes​

NívelO que cobreQuem escreveQuando rodaObrigatório em
UnitárioRegras internas do códigoDevA cada pushTodas as categorias
Cenário (aceitação)Cada cenário WHEN/THEN da spec, 1 cenário = 1 testeQA (dono), Dev apoiaA cada PR e no mergeTodas que têm delta da spec
RegressãoCenários da spec oficial já arquivadosPipelineA cada merge na mainTodas
Integração / contratoIntegrações com sistemas de clientesDev + QAA cada PR que toca a integraçãoMédia (integração), grande, crítica
SegurançaAnálise estática, dependências, revisão manualDevOps (automático) + Segurança (manual)A cada PR; manual na críticaAutomático: todas · manual: crítica

Regra de cobertura: a métrica que importa não é % de linhas, mas % de cenários com teste automatizado. A meta é 100% para cenários novos: um cenário sem teste não passa no G4.

Práticas de engenharia obrigatórias​

  • Revisão antes do código: a spec é revisada por PR (Fase 3) antes de qualquer implementação.
  • Code review em todo PR, por pelo menos 1 pessoa diferente do autor.
  • Pipeline verde para fazer merge: build, testes, openspec validate --strict e análise estática.
  • Nada de commit direto na main: tudo entra por PR (veja Gerência de configuração).
  • Código gerado por IA segue as mesmas regras e é responsabilidade de quem abriu o PR (IA).

Defeitos​

SituaçãoO que fazer
Defeito encontrado na Revisão ou ConstruçãoCorrigir na mesma change; se mudou a spec, soma 1 em Specs reabertas
Defeito encontrado após a releaseAbrir Bug ligado à change de origem (AB#id), com o cenário que faltou. O bug entra na Entrada como qualquer demanda (pequena, ou crítica se afetar cliente regulado)
Defeito grave em produçãoHotfix: rollback ou correção pelo fluxo de hotfix; análise na retrospectiva do processo

Todo defeito pós-release responde a uma pergunta na retrospectiva: qual cenário faltou na spec, e por que a revisão não o encontrou?

Indicadores de qualidade​

Medidos automaticamente (detalhes em Métricas): defeitos pós-release, % de specs reabertas, % aprovadas no gate na 1ª tentativa e % de cenários com teste automatizado.
