Métricas do processo

As métricas respondem ao sintoma "muitos dados, nenhuma métrica confiável" do diagnóstico e à recomendação R4. Elas são coletadas pelo pipeline e pelo Azure DevOps Analytics, sem planilha manual: quem trabalha no processo já gera os dados ao mover o work item e abrir o PR.

Como escolhemos (GQM)​

Usamos Goal-Question-Metric: primeiro o objetivo, depois a pergunta, só então a métrica. Métrica sem pergunta não entra.

ObjetivoPerguntaMétrica
PrevisibilidadeQuanto tempo o cliente espera? As estimativas estão melhorando?Lead time · Desvio de estimativa
QualidadeA qualidade chega à produção?Defeitos pós-release · % de cenários com teste
EficiênciaQuanto esforço perdemos com retrabalho?% de specs reabertas · Taxa de retrabalho
AderênciaOs gates estão claros e sendo cumpridos?% aprovadas no gate na 1ª tentativa

Sobre as metas

As metas da Release 1.0 são metas iniciais, definidas a partir do que o case descreve (estimativas que estouram 60–100%) e de referências de mercado. Depois de 3 releases com dados reais, o Comitê do Processo recalibra cada meta com a linha de base da Nexora, e a mudança entra no changelog.

Onde ver: o painel (AF11)​

Um dashboard único no Azure DevOps, igual para todas as equipes, com filtros por produto, equipe e categoria:

WidgetMostra
Lead time por categoriaMediana e percentil 85 das últimas releases
Cumulative FlowQuantos work items em cada estado (fase) e onde está o gargalo
Defeitos pós-releasePor release, com link para a change de origem
Gates% de specs reabertas e % aprovadas na 1ª tentativa
EstimativaDesvio de estimativa por categoria

A consulta base do lead time no Azure DevOps (WIQL) filtra work items Concluído na release, com os campos Categoria, Pronto em e Concluído em. O dashboard é configurado uma vez pelo DevOps e copiado para cada projeto.

Como as métricas são usadas​

  1. O painel (AF11) mostra a tendência por release.
  2. A retrospectiva do processo analisa a tendência e compara equipes e categorias.
  3. Os números de cada release entram no histórico organizacional.
  4. A melhoria escolhida vira uma change no repositório do processo.
Regra de uso

Métrica é usada para melhorar o processo, nunca para avaliar pessoas. Comparar equipes serve para descobrir qual prática funciona melhor e espalhá-la, não para ranquear quem trabalha mais.
